# shiro

shiro は Bun で動くローカル向けの AI チャット／コーディングエージェントです。ブラウザーから会話し、ファイル操作やシェルコマンドの実行を依頼できます。会話履歴は SQLite に保存されます。

## 必要なもの

- [Bun](https://bun.sh/)（このリポジトリでは Bun 1.4 系を使用）
- OpenAI Codex を利用できるアカウント（初回ログイン時にブラウザーで認証）

## セットアップと起動

```bash
bun install
bun run index.ts
```

`http://localhost:3000/` を開き、画面からログインしてください。ポートは `SHIRO_PORT` で変更できます。Web サーバーは `127.0.0.1` のみで待ち受けます。OAuth のコールバックにはローカルのポート `1455` を使用するため、ログイン時には空けておいてください。

エージェントの作業ディレクトリはサーバーを起動したディレクトリ（`process.cwd()`）です。上記の手順ではこのリポジトリが対象になり、ファイル操作の相対パスやシェルコマンドの実行場所の基準になります。

## 主な機能

- メッセージアプリ形式のチャット。エージェントは `send_message` ツールで吹き出しを送り、`react` ツールでユーザーのメッセージに絵文字のリアクションを付けます。ユーザーもエージェントの吹き出しにリアクションでき、次のメッセージでエージェントに伝わります。モデルと推論の強さを会話ごとに選択できます。
- DeLM に着想を得た最大4体の非同期エージェント。起動する数は未確保のタスクの数に従い、雑談や1体で済む依頼では1体だけが動きます。共有ノートとタスクキューを使い、同じチャットに名前付きで発言します。
- 画像添付、Markdown 表示、会話の編集・再生成。
- SQLite による会話履歴の保存。
- 会話をまたぐ長期共有文脈。参加者が `settle` ツールで、原因を確認済みで会話が終わっても成り立つ事実（環境の事実、利用者の継続的な方針）を残し、以後の会話の参加者に渡します。
- ターンの終了後に観察者がそのターンの記録を読み、type-gap（既存の gist の型で表せず、自由文などに歪めて書かれた状態）を報告として残します。用語は `GLOSSARY.md`、判断の理由は `docs/adr/` にあります。
- エージェント用ツール：ファイルの読み書き・編集（`read_file`、`write_file`、`edit_file`）、ディレクトリ一覧（`list_directory`）、ファイル名・内容検索（`search_files`、`search_text`）とシェル実行（`bash`）。基本の読み取り・検索はシェルやスクリプトを介さず専用ツールで実行します。
- シェルコマンドは `TYPESAFE_API_KEY` が未設定の場合、実行前に画面で承認します。設定すると、会話の「コマンドの自動承認」がオンの場合に、Jev が読み取り専用、または取り消し可能かつ依頼に沿うと判定したコマンドを自動実行できます。新しい会話ではこの設定は既定でオンです。ルールが危険とみなすコマンドや、Jev が承認しない・判定に失敗したコマンドは、自動実行せずユーザー確認に戻ります。
- API キー不要の `web_fetch` で公開 URL の HTML・プレーンテキストを取得できます（JavaScript 実行やログイン、PDF は非対応）。
- `PARALLEL_API_KEY` を設定すると Web 検索ツールが有効になります。検索結果の URL を回答に含めるようエージェントに指示します。

## 基本の読み取り・検索ツール

`read_file({ path, start_line?, end_line? })` は UTF-8 テキストを読みます。行番号は1始まり・両端を含み、省略時はファイル全体が対象です。元の改行を保ち、行番号は追加しません。出力は50,000文字、走査は8 MiBまでで、超過時は切り詰めを明記します。通常ファイルのみ対象です。

`list_directory({ path })` は直下の項目を並べます。隠し項目も含み、ディレクトリは `/`、シンボリックリンクは `@` を付けます。`search_files({ path, pattern })` は `rg --files --glob` でファイルパスを検索します。`search_text({ path, pattern, regex?, glob? })` は `rg` で内容を検索し、`path:line:本文` を返します。既定は文字列の完全一致検索で、`regex: true` なら正規表現として扱います。

検索には PATH 上の [ripgrep（`rg`）](https://github.com/BurntSushi/ripgrep) が必要です。設定ファイルやシェルは使わず固定引数で直接起動し、`rg` がなければエラーにします。通常の ignore・隠しファイル除外は `rg` に従いますが、明示した glob やパスは除外を上書きする場合があります。ディレクトリ内のシンボリックリンクは追跡しません。内容検索はバイナリや2 MiB超のファイルを除外し、1ファイル200一致まで・実行10秒までで出力にも上限があります。一覧・検索の上限超過は出力に明記します。

これらは読み取り専用ツールで、`bash` の承認・Jev 判定を必要としません。Code Mode 内からも同じ API を利用できます。シェル操作の承認や危険操作のブロックは従来どおりです。

## Code Mode（ローカル実行）

複数のツール呼び出しと結果の加工を、モデルが生成した JavaScript にまとめる `execute_code` を追加しています。[Cloudflare Code Mode](https://developers.cloudflare.com/agents/tools/codemode/) の方式に着想を得たローカル実装で、Cloudflare の SDK や Workers への接続は使いません。直接の `read_file` や `bash` も引き続き使えます。

Linux、ユーザー名前空間を利用できる `bubblewrap`（`bwrap`）、`prlimit`（util-linux）、Node.js が必要です。Node.js 26 で検証しています。Node の permission モードなど必要な起動フラグが使えない場合や、OS が名前空間の作成を拒否する場合はエラーになり、隔離を省いた実行には切り替えません。依存コマンドが PATH にあれば既定でツールを公開し、`SHIRO_CODE_MODE=0` で無効化できます。

モデルが渡す `code` は次のような **JavaScript の async 関数式**です。TypeScript の型注釈は使えません。有効なツールの型宣言と説明は `execute_code` のツール説明に含まれます。

```javascript
async () => {
  const texts = await Promise.all([
    tools.read_file({ path: "README.md" }),
    tools.read_file({ path: "package.json" }),
  ]);
  return texts.map((text, i) => ({ file: i, firstLine: text.split("\n")[0] }));
}
```

`tools.*` は既存ツールと同じ文字列を返します。すべての呼び出しを await し、必要な結果を return してください。最終出力は `{ result, logs }` の JSON です。ツール失敗は通常 `error: ...`、コマンド拒否は `user denied this command` という文字列になるため、コード側で必要に応じて確認します。

生成コードは別プロセスで実行し、bubblewrap でホーム・作業ディレクトリ・ホストの一時ディレクトリ・環境変数・外部ネットワークから隔離します。読み取り専用のランタイム用ディレクトリ（存在する `/nix/store`、`/usr`、`/bin`、`/lib`、`/lib64` と ld.so キャッシュ）は見えます。Node の `vm` 自体は安全境界として扱いません。追加の Node permission モードで直接のファイル書き込み・子プロセスや Worker の作成を拒否します。ファイル操作や通信が必要な場合はホスト側の `tools.*` を経由します。これらのツールの権限は従来どおりで、特に `bash` はホスト上で動き、既存の承認・Jev 判定を通ります。

承認待ちを含む実行時間は120秒、CPU時間は60秒、仮想アドレス空間は1 GiB、V8ヒープは64 MiBに制限しています。ツール呼び出しは最大100件・同時8件で、コード・RPC・結果・ログにもサイズ制限があります。`execute_code` の再帰呼び出しは禁止です。書き込みとシェルは既存の副作用キューで直列化し、内側の操作も画面と実行トレースに記録します。停止・タイムアウト時には生成コードを強制終了し、未承認・待機中の操作を無効化しますが、すでに完了した副作用の巻き戻しはしません。

## グループチャットと協調実行

通常どおり起動し、メッセージを送ると、同じモデル・推論設定を使う `shiro-1`〜`shiro-4` のうち必要な数だけが応答します。タスクキューは空で始まり、最初に動くのは `shiro-1` だけです。次の参加者は、未確保のタスクがあり、かつ先の参加者がタスクを確保して担当を共有ノートまたは吹き出しで表明した（または終了・失敗した）ときに、最新の共有文脈を読んで起動します。起動後の処理は並行します。未確保のタスクが出ないままほかの参加者が全員終了すると、残りは起動せず「出番なし」になります。全員停止では開始待ちの参加者も停止します。既存の会話も次の入力からこの動作になります。画面のレイアウトはそのままで、吹き出しに参加者名と色、画面下部に各参加者の入力中表示を付けます。発言は送信された順に並び、リアクション、編集、再生成、コマンド承認、全員の停止も従来の操作で使えます。

- 中央の指揮役は置かず、各モデル呼び出しの前に最新の共有ノート・キュー・参加者状態を渡します。各参加者は独立したターン内履歴とセッション ID を持ちます。
- `team` ツールの `read / add / claim / complete / release / publish` で協調します。タスクの確保は単一プロセス内で原子的に行い、他者のタスクを完了・解放できません。初期タスクはなく、作業が独立した部分に分かれるときに参加者がタスクを追加します。
- 吹き出しも共有ノートに即時反映します。共有キューとノートは SQLite の `board` 列に保存し、次のユーザー入力では新しいキューを作ります。公開した発見はターン終了時に共通履歴にも残しますが、各参加者のツール履歴や暗号化推論はターンをまたいで保存しません。
- 開始待ちの参加者は共有文脈ページで「開始待ち」と表示します。各参加者がツールなしで応答を終えるとその参加者は終了し、全員が終了するとターン完了です。未完了の確保タスクは終了時に解放し、作業中の参加者は確保できますが、そのタスクのために新しい参加者は起動しません。終了した参加者を自動で再起動する仕組みもありません。各参加者のモデル呼び出しは1ターン最大40回です。複数の参加者が起動したターンは、その分 API 利用量が増えます。

これは [DeLM](https://arxiv.org/abs/2606.10662) の共有コンテキストと非同期キューを取り入れた最小実装であり、論文の完全再現ではありません。独立したコンテナー／ワークスペース、解の選択や自動マージ、複数マシンへの分散、再起動後の処理再開は未実装です。同じ作業ディレクトリで動くため、同一ターン内のファイル書き込み・編集・シェル実行は直列化していますが、古い読み取り結果に基づく上書きや、別会話・外部プロセスとの競合までは防ぎません。

## 共有文脈ページ

会話を開いて上部の「共有文脈」を押すと、`/c/:id/context` が開きます。ページは「ボード」「スキーマ」「記録」の3つのタブに分かれます。「ボード」ではタスクキュー・担当・結果・参加者状態・共有ノートを確認できます。実行中は WebSocket で自動更新し、「チャット」で元の画面に戻ります。ノートは通常の共有情報、`[failure]`、`[type-gap]`、`Chat:` の暫定ラベルで絞り込め、タスクも含めた検索とボードの JSON コピーができます。

「ボード」の表示対象は **最新ターンのボード** で、ノートは最大40件です。過去ターンの完全なアーカイブや非公開の推論・全ツール履歴を表示するものではありません。失敗記録はエージェントが公開したものだけで、すべてのエラーの自動記録ではありません。`[type-gap]` のラベルは v0 のノートの書き方です。最新ボードの型付き gist も表示します。「スキーマ」と「記録」は会話をまたぎます。「スキーマ」には型の提案（採用・却下のボタン付き）と採用済みの型を、「記録」には type-gap report、長期共有文脈、ターンの記録、ラベル付きノートを表示します。未決の提案があると、「スキーマ」のタブに件数が付きます。

## フォント

本文・見出し・フォーム・コード表示は LINE Seed JP に統一しています。[公式配布](https://seed.line.me/index_jp.html)の Regular / Bold を `web/fonts/` に同梱し、外部フォントサービスを使わず配信します。ライセンスと出典は `web/fonts/OFL.txt` と `web/fonts/README.md` にあります。コードも等幅ではなく LINE Seed JP となり、未収録の絵文字などはシステムフォントへフォールバックします。

## 設定（環境変数）

| 変数 | 用途 | 既定値 |
| --- | --- | --- |
| `SHIRO_PORT` | Web サーバーのポート | `3000` |
| `SHIRO_CODE_MODE` | `0` でローカル Code Mode を無効化 | 依存コマンドがある Linux で有効 |
| `SHIRO_MODEL` | 新しい会話で使う既定モデル | `gpt-6.1-sol`（`shared.ts` のモデル一覧の先頭） |
| `SHIRO_CODEX_URL` | Codex API の接続先 | `https://chatgpt.com/backend-api/codex` |
| `SHIRO_DB` | SQLite データベースのパス | `~/.shiro/shiro.db` |
| `SHIRO_AUTH_FILE` | OAuth 認証情報ファイルのパス | `~/.shiro/auth.json` |
| `PARALLEL_API_KEY` | 設定すると Web 検索を有効化 | 未設定（無効） |
| `SHIRO_PARALLEL_URL` | Web 検索 API の接続先 | `https://api.parallel.ai/v1/search` |
| `TYPESAFE_API_KEY` | 設定すると Jev によるコマンド判定を利用可能 | 未設定（無効） |
| `SHIRO_JEV_URL` | Jev API の接続先 | `https://api.typesafe.ai/v1/systemone` |
| `SHIRO_JEV_MODEL` | Jev の判定モデル | `jev-1.14.0` |

Bun は `.env` を自動で読み込みます。API キーなどの秘密情報は `.env` に置き、共有・コミットしないでください。OAuth 認証情報ファイルは `0600` の権限で保存されます。

## 開発・確認

```bash
bun check     # 型チェック
bun test      # テスト
```

`bun run typecheck` でも型チェックできます。`index.test.ts` は、ファイル編集の一意一致、JWT からのアカウント ID 抽出、会話イベントの reducer、危険なコマンドの静的判定、検索結果の整形を検証します。`team.test.ts` はタスク所有権と参加者ごとのイベント分離、`agent.test.ts` はモデル通信をモックして並行実行、承認の分離、一括停止、削除、片方の失敗を検証します。ランタイムのテストには一時 SQLite を使います。`web/thread.test.tsx` はサーバー側描画で発言順、参加者名、承認待ち表示を確認します。`web/context.test.tsx` は共有文脈ページの分類・描画・空状態を確認し、`agent.test.ts` はボード更新イベントのスナップショットも検証します。OAuth・外部 API との接続やブラウザー UI の E2E テストは含まれていません。

### 処理の流れ

1. `index.ts` が `web/index.html` と API を配信し、同一オリジンの WebSocket で会話イベントをブラウザーへ push します。
2. `agent.ts` が会話と参加者ごとの実行ループを管理し、`instructions.ts` の指示と共有文脈を `codex.ts` に渡します。モデルからのツール呼び出しは `tool-runner.ts` が処理し、`tools.ts` の登録ツールと `approve.ts` のコマンド判定を利用します。
3. `store.ts` が UI 表示用のメッセージ（`messages`）とモデルに渡す履歴（`items`）を分けて SQLite に保存します。`shared.ts` の型とイベント reducer はサーバーと UI で共有され、サーバーの会話状態とブラウザーの表示に同じイベントを適用します。
4. `web/app.tsx` が画面を組み立て、各 UI コンポーネントが `sync.ts` を通じて API・イベントと同期します。HTML・TSX・CSS は Bun が `web/index.html` の import から処理するため、フロントエンド専用のビルドサーバーは不要です。

モデルへのリクエストは、応答にツール呼び出しが含まれる間繰り返します。`codex.ts` は複数のツール呼び出しをモデルに許可していますが、`agent.ts` は各参加者内では受け取った呼び出しを順番に実行し、参加者同士のモデル通信は並行します。同じ会話で同時に実行できるターンは一つで、別の会話のターンは並行して実行できます。

画面の吹き出しは `chat.ts` の `send_message` から作られます。モデルが通常のテキスト出力として返した内容は履歴には保持しますが、現在の UI には表示しません。`steps.tsx` は API から届く推論要約とツール実行情報を扱いますが、現在は CSS で非表示にし、承認カードだけを表示します。モデル内部の推論そのものを表示する機能ではありません。

編集・再生成は会話を分岐として残す方式ではなく、対象ユーザーメッセージの直前まで表示用・モデル用の履歴を巻き戻してから、その先を作り直します。すでに行われたファイル変更やコマンドの副作用は巻き戻しません。

### モジュールの境界と変更箇所

```text
web/index.html → web/app.tsx → 各 UI コンポーネント
                              ↕ web/sync.ts（REST / WebSocket）
                            index.ts
                              ↓
                            agent.ts → codex.ts → auth.ts
                              ├── store.ts → SQLite
                              ├── instructions.ts
                              └── tool-runner.ts
                                    ├── approve.ts → Jev（任意）
                                    └── tools.ts → chat.ts / team.ts / search.ts / fetch.ts / ファイル操作・bash

shared.ts：サーバーと UI が共有する型・設定・イベント reducer
toolkit.ts：各ツールの定義・実行コンテキスト・表示情報の契約
```

- **API を変更する場合**：`index.ts` と呼び出し側の `web/sync.ts` を確認します。会話ターンや編集・再生成・停止の制御は `agent.ts` の責務です。
- **会話方針を変更する場合**：`instructions.ts` に通常会話とチーム協調の指示をまとめています。プロンプトの変更と、会話状態やツール実行の仕組みの変更は分けて扱います。
- **ツールを追加する場合**：`toolkit.ts` の `Tool` 型に沿って定義し、`tools.ts` の `ALL` に登録します。定義にはモデル向けの説明・実行処理・UI 用の表示情報をまとめます。通常は UI 側にツール名ごとの分岐を追加する必要はありません。承認が必要なシェルコマンドは `command` で指定します。実行・承認の手順を変更する場合は `tool-runner.ts` を確認し、承認待ちの管理と副作用の直列化キューは `agent.ts` のターン単位で共有します。
- **会話イベントを追加する場合**：`shared.ts` の `Ev` と `apply`、イベントを発行する `agent.ts` / `tool-runner.ts`、表示する UI を合わせて変更します。`web/sync.ts` は連番でイベントの欠落を検出し、会話を再取得して同期します。
- **画面を変更する場合**：`web/app.tsx` が組み立て、`thread.tsx` が会話、`steps.tsx` が推論要約・ツール実行、`composer.tsx` が入力と設定を担当します。スタイルも各コンポーネントに対応する CSS に分かれています。

### 永続化とメモリー上の状態

`store.ts` は会話のメタデータ・表示用メッセージ・共通のモデル用履歴・最新ターンの共有ボードを保存し、読み込んだ会話をメモリーにキャッシュします。生成中のイベントは逐次 UI に配信されますが、SQLite への保存は主にターン開始時・終了時、共有ボード更新時、設定変更時であり、イベントごとの永続化ではありません。異常終了時には途中の生成内容が失われる場合があります。

これとは別に、`substrate` テーブルへ基質ログを追記します。ユーザー入力、`team` の `add / claim / complete / release / publish`、それ以外のツール呼び出し（引数と結果）を1行ずつ記録し、各行にスキーマの版番号 `v`（現在は 3）、会話 ID、ターン ID、参加者名を付けます。行の書き換えと削除は行いません。ボードの作り直し、40件の上限、編集・再生成による巻き戻しの影響を受けず、**会話を削除してもこのログは残ります**。ファイルの内容やコマンド出力がツール結果として含まれるため、消す場合はデータベースを直接操作してください。参加者の起動も `start` として記録します。共有文脈ページの「記録」タブが全会話のログを読み出します。「ターンの記録」はターンごとの起動数、追加されたタスク数、ツール呼び出し数、type-gap と `[failure]` の件数の表で、「ラベル付きノート」は `[failure]` と v0 の `[type-gap]` で始まるノートの本文です。「この会話」を選ぶと、type-gap report、定着事項、ターンの記録、ラベル付きノートを、開いている会話のものに絞り込みます。API は `GET /api/colony` です。

基質スキーマの v0 は gist の型がノートとタスクだけの状態で、v1 は次の3種類の行を足したものです。v0 の行はそのまま読めます。

- `type-gap`: type-gap report。書きたかった状態、歪め方、調整コスト（未計測可）、根拠、出どころ（`self` は参加者の `report_type_gap`、`observer` は観察者）を持ちます。
- `settled`: 定着事項。本文、種類（`environment` / `policy`）、観測した作業ディレクトリ（`null` はディレクトリを問わない）を持ちます。
- `retract`: 打ち消し。対象の定着事項の番号と理由を持ちます。打ち消された定着事項は行として残り、参加者には渡されなくなります。

v2 は、タスクに `files`（持ち主が編集するファイルのパスの一覧）を足したものです。`team` の `add` と `claim` で書きます。ファイル単位の編集範囲をタスク本文やノートの自由文に書く歪みが、過去18ターンの type-gap report 16件中7件、3会話すべてで検出されたため、利用者の決定で追加しました。他の参加者の編集を止める仕組みはなく、参加者がボードを読んで避けます。

打ち消されていない定着事項のうち、現在の作業ディレクトリで観測されたものとディレクトリを問わないものを、全参加者の全モデル呼び出しに渡します。1件は300文字までで、件数の上限はありません。どの参加者も打ち消せます。

観察者は、gist が1件以上書かれたターンの終了後に、会話のモデルを推論の強さ `low` で1回呼びます。吹き出しだけのターンでは呼びません。結果は `observe` 行（報告の件数、または失敗の内容）として残ります。報告は根拠の gist を1件以上指すものだけを採り、正誤の判定はしません。共有文脈ページの「記録」タブにある「観察する」は、まだ観察されていない過去のターンに同じ処理をサーバーの裏で適用します（ターンあたり最大1回のモデル呼び出し。1件失敗した時点で止まります）。進み具合はページに表示され、途中で中止できます。ターンを実行中の会話は対象から外れ、そのターンは終了時に観察されます。

v3 からは、型をコードではなく基質のデータとして足します。まだ提案に使われていない type-gap report が10件たまると、観察者の後に `evolver.ts` が会話のモデルを推論の強さ `low` で2回呼びます。1回目で型を提案し（`type-proposal` 行）、2回目でリプレイとして各 report がその型の欄で書けるかを判定します。どの report にも当てはまらない提案は捨てます。提案は、対応する report の番号と、スキーマ肥大コスト（欄の数と、定義のバイト数）を持ちます。採用はまだ自動では行わず、利用者が共有文脈ページで決めます。同じページに、未決の提案、たまった report の数、採用と却下のボタン、件数に関係なく今すぐ提案と評価を実行するボタンがあります。今すぐ実行する場合は既定のモデル（`SHIRO_MODEL`）を使います。観察者、進化の実行、過去ターンの観察のためのコマンドはなく、すべてサーバーの起動中に画面から操作します。

採用された型は、参加者のプロンプトに欄と読み手の義務とともに渡り、`write_gist` ツールで書けます。書いた gist はボードの `gists` に載ります。サーバーの再起動は要りません。採用と却下は取り消せません。提案に使った report は、提案の有無にかかわらず次の提案には使いません。理由は docs/adr/0003 にあります。

実行中のターン・承認待ち・イベント連番はメモリー上の状態です。ユーザーのリアクション自体は保存しますが、それを次の入力時にモデルへ伝えるための通知はメモリー上にあるため、再起動を挟むと失われます。UI のテーマや新規会話向けの設定はブラウザーの `localStorage` に保存します。

`.env` と `node_modules/` はローカルで使うもので、リポジトリには含めません。

### Web ページ取得

`web_fetch` は URL を1つ受け取り、最終 URL・タイトル・静的な本文テキストを返します。API キーは不要で、検索結果やユーザーが指定したページの内容を確認するために使います。HTML はスクリプト・スタイル・ナビゲーションなどを除いてテキスト化しますが、記事本文だけを選ぶ Readability ではなく、JavaScript で生成される内容は取得しません。HTML・XHTML・プレーンテキスト以外、圧縮された応答、未対応の文字コードはエラーにします。

取得全体は30秒、応答は2,000,000バイト、返す本文は20,000文字までです。サイズ超過は取得エラーとし、抽出本文が長い場合は切り詰めたことを結果に明記します。リダイレクトは最大5回まで追跡し、移動先も毎回検証します。HTTP(S)の標準ポートだけを許可し、認証情報付き URL、localhost・プライベート／予約 IP を拒否します。DNS の全応答を検証し、接続時は検証済み IP に固定します。これはこのツールの制限であり、`bash` などを含むエージェント全体の通信サンドボックスではありません。

Cookie や保存されたログイン情報は送りません。ページ中のリンク・画像なども自動取得しません。ただし、URL 自体（パスやクエリを含む）は取得先に送信されるため、秘密情報を含めないでください。ページ本文は信頼できない外部データとして扱い、そこに書かれた命令には従わないようモデルに指示します。

## 安全上の注意

サーバーはループバックアドレスで待ち受け、API・WebSocket では Host / Origin の検証も行いますが、エージェントはこのプロセスのユーザー権限でファイルを読み書きし、シェルコマンドを実行します。作業ディレクトリ内だけに制限するサンドボックスではありません。

実行前の承認・Jev による判定の対象はシェルコマンド（`bash`）です。ファイルの読み書き・編集ツールは承認なしで実行されます。また、Web 検索では検索内容が Parallel に、自動承認の判定ではコマンド・作業ディレクトリ・ユーザーの依頼文が TypeSafe に送信されます。これらを踏まえ、信頼できる環境で利用してください。
